Reads mutations straight from your annotated features — no Ensembl, no transcript alignment, promoter mutations supported. The base change is taken from the feature label (e.g. -146C/T, P301L_C>T). Labels with only a protein change (L444P) are reported for you to re-annotate with the base change.

Silent bystander variants (and Top-N per mutation) are set at the top under Library options — they apply to this step-by-step run too.

↓ Download batch.csv

Look up variants (recommended)

Paste names exactly as papers write them — GENE, PROTEIN_CHANGE, one per line. This queries ClinVar and shows every matching variant with its GRCh38 coordinate, rsID and transcript. You choose — nothing is auto-selected, because one protein change can map to several distinct variants. Legacy numbering is handled (GBA1 N370S and N409S both resolve).

Non-coding sites (TERT promoter) have no protein change — give those as genomic coordinates below.

Input formats — least ambiguous first

A variant is only meaningful relative to a transcript, and the same position numbers differently across transcripts (the MAPT trap: 441 aa vs the 758 aa canonical). Prefer inputs that carry their own coordinate system.

  • Genomic (best) — chr1:g.155235252A>G — transcript-free; also the only option for promoter / non-coding sites
  • rsID — rs76763715
  • Versioned transcript c. — NM_000157.4:c.1448T>C or ENST00000368373.8:c.1226A>G
  • Gene + transcript + protein — line GBA1, NM_000157.4, L483P

Avoid — a bare protein change or bare c. with no transcript (GBA1, L483P or c.1234A>G). These are transcript-dependent; the tool will not guess canonical — it reports them as skipped and asks for a transcript. To deliberately use canonical, put canonical in the transcript field.

Each line is either a self-contained variant (genomic / rsID / NM_|ENST:c.) or GENE, TRANSCRIPT, MUTATION (comma or space separated). Bare protein / c. changes need a transcript — see above. Or upload a file with a gDNA_mutation column (add a transcript column for coding changes).

2

Run PRIDICT2.0

on your machine

Prediction is heavy and runs in its own conda environment, so it stays on your machine. Put the downloaded batch.csv in the PRIDICT2 input/ folder, then run:

python pridict2_pegRNA_design.py batch \ --input-fname batch.csv \ --cores 3 \ --summarize K562 \ --summarize_number 10

Takes ~1–2 h on a laptop CPU for a few hundred sequences. When it finishes, grab the *_summary_K562_batch_summary.csv from predictions/.

…or let the app run it for you (Layer 1 automation). This copies the Step 1 batch.csv into PRIDICT's input/, runs it in the pridict2 env, and reads the summary back — Step 3 then builds straight from it, no re-upload.

Names this run's input file (input/<name>.csv) so its summary is identifiable. The previous run's output is moved into predictions/_archive/ automatically — no need to empty the folder yourself.

PRIDICT's --summarize_number: how many top pegRNA candidates it keeps per target in the summary. This is the PRIDICT-level pool; the final library then takes Top-N per mutation from it (set in Library options).

Heads-up: this blocks until PRIDICT finishes. On a long run the browser may show a timeout while it keeps going on disk — if that happens, the summary still appears in predictions/ and you can upload it in Step 3 as usual.

Alternative engine — OptiPrime

Score the same Step 1 batch.csv with OptiPrime (David Liu lab) instead of PRIDICT2.0. OptiPrime runs in its own optiprime conda env. The rest of the workflow (Step 3 assembly, QC, download) is identical — Step 3 builds from whichever engine you ran last.

These describe YOUR experiment. OptiPrime scores the same pegRNA differently depending on them, so a mismatch here shows up as a wrong efficiency, not as an error. PEmax is the Cas9 setting — leave PE system on PE2 unless you co-express MLH1dn (that is PE4).

Also blocking. OptiPrime searches protospacers for each edit and scores their PBS/RTT designs independently of PRIDICT.
